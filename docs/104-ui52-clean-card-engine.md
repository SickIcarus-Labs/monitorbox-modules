## Actual architectural deletion boundary

New schema-v5 GENERATED cards must never invoke `v1-parity.js::parityCoreCard`, `v1-beta-polish.js::parityNetworkChildren` or `parityPowerRows` to determine displayed members, readings, ordering, count or height. Remove those functions from new-card rendering/admission and any dependence on UniFi `metadata.front_page`, stale site-specific six-device lists or old fixed 185/135/95 heights. Preserve existing drawer navigation/actions, canonical health, camera reconciliation, UPS/outage diagnosis, WAN/DNS truth and raw monitoring checks; if their rendering is still in v1 files, isolate detail-only compatibility rather than delete legitimate functionality. V1-v4 snapshots remain byte-for-byte restorable and unsupported/future schema fails closed; a historical card is not a template for new cards.

One common module-owned, provider-neutral **current capability → normalized card definition** projection drives: wizard-completion initial dashboard, explicit Reset/Regenerate dashboard on an existing configured site, homepage, Arrange, editor, and captured revisions. Initial bootstrap and later Reset must produce the same normalized card definitions and initial automatic placement when given equivalent current site/configuration/discovery/live capability input; neither pathway reads stale prior card selections or positions. Reset targets the selected site by default, with explicit all-sites scope for multisite operators. It discards only dashboard card content/membership/placement preferences in scope; monitoring, module credentials, checks, graphs and other site preferences stay intact. Reset stages a draft, then uses the existing authenticated Validate → Preview → Apply flow to make one recoverable canonical revision; historical revisions/snapshots are unaffected. Define explicit card member IDs, default selections, native summaries vs optional readings, LIVE series key/units/cadence, hidden/compact state, and stable layout. No renderer-specific fallback which silently changes selections. Show all checked eligible members (do not truncate at six); ineligible `remote_site` objects cannot be checked in a Network card unless a supported remote-site component actually renders. An explicitly added host/gateway earns a card; module-discovered children stay grouped. Third-party module families have the same generic inclusion contract.

Network: determine eligible site-local network devices from the current canonical object/capability inventory, not legacy `front_page`; initial checked list is explicit and complete. Power: two present UPS members and their available native charge/runtime/load/voltage readings must be honestly reflected as default card content; no phantom empty selections. Internet: native WAN/DNS diagnostic summary (from Core health semantics) is an explicit generated content type; add advertised LIVE WAN traffic only when actually supported. Cameras: visible member IDs must exactly control visible camera rows, while the card may separately state full monitored-site health/count; do not conflate site-wide with shown. Hosts: preferentially select confirmed matching current 1-Hz LIVE CPU and memory metrics from the advertised series catalogue; otherwise select truthful observed state with 15-s cadence and correct units. Keep user-custom LIVE selections exact and untouched across upgrades.

Initial 3/2/1 packing derives from generated card content and measured DOM height once per layout/viewport change, not from fixed family archetypes or 1-Hz measurement updates. Arrange uses the identical homepage renderer, with the already accepted one grip above each card; tap/drag, Undo/Cancel and one authenticated Apply continue to work. No background destructive reinitialization after a saved v4/v5 layout, upgrade, refresh or snapshot restore. The *only* user-initiated reset is the explicit Reset/Regenerate dashboard operation; installation alone never triggers it.
